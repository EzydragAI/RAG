What is RAG?

The Problem & Solution

Large Language Models (LLMs) have a knowledge cut-off date and are prone to hallucination when asked about private, proprietary, or highly recent data.

RAG (Retrieval-Augmented Generation) acts as an open-book test. It forces the LLM to search for and read relevant external documents before answering, anchoring its response in verifiable facts.

A Concrete Example

Without RAG (Blind Guess):

User: What is my PTO balance?

LLM: I don't have access to your personal HR data.

With RAG (Open Book):

1. System auto-retrieves: [User_John_HR_File.pdf]

2. Prompt tells LLM to read the file.

3. LLM: John, you have 15 days of PTO remaining.

The RAG Iceberg

Building a basic RAG prototype takes just a few hours. This is the tip of the iceberg—LangChain tutorials, simple PDFs, and basic vector stores.

Making RAG work reliably in enterprise production is a massive engineering challenge. The underwater structure requires advanced techniques like chunk optimization, query reformulation, cross-encoder reranking, and secure access controls.

Phase 1: Beginners

The Tip of the Iceberg. Setting up the fundamental data retrieval pipeline.

The Art of Chunking

LLMs have strict limits on how much text they can read at once (the context window). We cannot pass a 500-page manual into a prompt.

Chunking is the process of breaking large documents into smaller, digestible pieces. How you chunk deeply affects accuracy.

  • Fixed-Size Chunking: Splitting every 500 words. Fast, but might cut a sentence or paragraph in half, destroying context.
  • Semantic Chunking: Splitting intelligently by paragraphs, headers, or sentences.
  • Chunk Overlap: Taking the last 50 words of Chunk A and starting Chunk B with them to preserve flow.

Vector Embeddings & Similarity

Once chunked, an embedding model (like OpenAI's `text-embedding-3-small`) translates the text into a dense numerical array—often 768 to 1536 dimensions long.

This places the concept of the text into high-dimensional space. "Apple" (fruit) and "Apple" (company) are placed in entirely different areas based on their semantic meaning.

To find the most relevant chunk, the DB calculates the angular distance between the User's Query Vector and the Document Vectors using Cosine Similarity.

The Generation Engine (Prompt Injection)

How does the LLM actually "read" the documents? Through a technique called Prompt Injection or Context Stuffing.

Orchestrators like LangChain act as the middleman. They take the chunks returned by the Vector DB and programmatically stitch them into a massive System Prompt alongside the user's original query.

We apply strict "guardrails" in the prompt, commanding the LLM to only use the provided context and to admit ignorance if the answer isn't there, practically eliminating hallucinations.

Phase 2: RAG for Builders

Diving below the surface. Transforming a fragile prototype into a secure, production-ready system.

Security & PII Masking

Production RAG requires strict data privacy. Before sensitive enterprise documents are embedded and sent to external LLMs, they must be scrubbed.

Personally Identifiable Information (PII) is programmatically masked to ensure compliance with GDPR and HIPAA regulations.

Before Masking:

"Contact John Doe at 555-0192 for the secret project details."


After Masking:

"Contact [PERSON] at [PHONE_NUM] for the secret project details."

Advanced Retrieval Tech

Query Reformulation

Users often ask vague follow-up questions. RAG systems use a smaller LLM to rewrite the query by analyzing the chat history, ensuring the Vector DB has full context for the search.

User: "How do I fix it?"

Reformulated: "How do I fix the Error 404 on the login page?"

Multi-Hop Retrieval

For complex logic, the system retrieves a document, finds a clue, formulates a new search, and repeats the process until the final answer is pieced together.

Q: CEO of the company that makes the iPhone?

Hop 1: Apple makes the iPhone.

Hop 2: Tim Cook is CEO of Apple.

Reranking (The Funnel)

Vector DBs (Bi-encoders) are incredibly fast because embeddings are pre-computed. However, they can lack precision. If you retrieve 100 documents, the perfect answer might be ranked #45.

To solve this, we use a Funnel Effect with a Cross-Encoder:

  • Broad Net (Bi-Encoder): DB fetches top 100 chunks instantly based on vector geometry.
  • Deep Score (Cross-Encoder): A slower, highly accurate ML model reads both the Query and each chunk simultaneously to score exact contextual relevance.
  • Refined Output: Only the absolute top 3 chunks survive the funnel to reach the LLM.

Beyond Vectors: GraphRAG

Standard RAG fails at global, big-picture questions (e.g., "Summarize the main themes of the entire dataset") because vectors only fetch isolated, specific snippets.

GraphRAG uses an LLM to extract entities (people, places, concepts) and their relationships, building a Knowledge Graph before querying.

When a user asks a question, the system navigates this web of connected nodes. This allows the AI to synthesize complex answers across thousands of documents, understanding how different entities interconnect.

Hybrid Search: The Best of Both Worlds

Dense Vector Embeddings are amazing at understanding meaning, but they often fail miserably at exact keyword matching. If a user searches for "Error Code ID-993A", an embedding model might return chunks about general errors, completely missing the specific ID.

Sparse Search (BM25): Traditional keyword search that excels at exact matches but fails if the user uses a synonym (e.g., searching "vacation" when the document says "holiday").

Hybrid Search runs both simultaneously. It blends the semantic understanding of vectors with the precise matching of keywords, merging the scores (using algorithms like Reciprocal Rank Fusion) for the ultimate results.

Under the Hood: HNSW Indexing

If you have 10 million chunks, comparing your query to every single document one-by-one (K-Nearest Neighbors) would take forever. Vector databases must be fast.

To solve this, they use Approximate Nearest Neighbor (ANN) algorithms. The industry standard is HNSW (Hierarchical Navigable Small World).

  • Layered Graphs: HNSW creates multiple layers of graphs.
  • The Highway (Top Layer): The top layer has very few nodes with long connections, allowing the search to quickly jump to the right "neighborhood."
  • The Local Streets (Bottom Layer): As the search drops down through the layers, the node density increases, allowing for precise, millimeter-accurate similarity matching in milliseconds.

Evolution: Agentic RAG & Routing

Standard RAG forces every single question through the same Vector Database. But what if the user asks about the weather today? The Vector DB won't know.

Agentic RAG introduces a highly intelligent "Router Agent" (an LLM functioning as a decision maker) at the very front of the pipeline.

The Agent analyzes the user's intent and decides which tool to use:

  • Query: "What is our Q3 revenue?" ➔ Routes to SQL Database.
  • Query: "Who won the game last night?" ➔ Routes to Web Search API.
  • Query: "How does the HR policy work?" ➔ Routes to Vector DB (Standard RAG).

Evaluation & Constraints

Evaluation Metrics (RAGAS)

You cannot improve what you cannot measure. Frameworks like RAGAS test two main pillars:

  • Context Precision: Did the database actually fetch the correct document?
  • Faithfulness: Did the LLM make up facts outside the provided context?

Hardware & Latency Tradeoffs

Advanced RAG is heavy. Adding Cross-Encoders and Graph traversal drastically increases wait times and API costs.

Builders use Semantic Caching (saving exact previous answers) to instantly serve repeated questions, bypassing the LLM entirely to save money.
